## What it detects

Reports files, SQL rows, statements and transactions, HTTP response bodies,
and gzip/zlib writers not released on every return path, including when a
helper is expected to close them.

Some cases are deliberately not reported:

- a resource returned, stored beyond the function, or passed to code gohawk cannot see into;
- a resource handed to asynchronous work through a helper;
- channel timers and tickers, which the garbage collector reclaims;
- a file, response body, or rows value opened once in `main.main`, which program exit closes;
- helper cleanup selected by a constant flag or `nil` option, such as `finish(file, nil)`;
- a `BeginTx` transaction whose context's cancel is called or deferred on every path.

The full list of precision boundaries, with the fixtures that pin each one, is
in the [resourcelifetime design notes](https://github.com/kojah/gohawk/blob/main/docs/development/analyzers/resourcelifetime.md).

## Why this is flagged

Owned resources are limited and often hold work open elsewhere. Missing cleanup
on even one return path can leak file descriptors, database connections,
network bodies or transactions until the program slows down or fails.

Further reading: [Effective Go: Defer](https://go.dev/doc/effective_go#defer),
[Package net/http](https://pkg.go.dev/net/http#Response).

## How to fix it

As soon as a resource is acquired successfully, arrange for its matching
cleanup on every later return path. Use `defer` when the current function owns
the resource, or transfer it only when the receiver clearly takes ownership.

### Accepted code

```go
func readSafely(path string) error {
  file, err := os.Open(path)
  if err != nil {
    return err
  }
  defer file.Close()
  return nil
}
```
