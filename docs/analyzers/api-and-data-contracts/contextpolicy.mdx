## What it detects

Reports `context.Context` parameters that are not first, contexts stored in
structs, and calls that pass a definitely nil context. In supported test code,
the opt-in test check reports detached goroutines whose cancellation path is
rooted in `context.Background()` or `context.TODO()`.

### Checks

{/* gohawk:generated-checks:start */}
| Check | What it detects |
| --- | --- |
| <CheckIdentity name="context-first" /> | Reports context.Context parameters that are not first. |
| <CheckIdentity name="context-storage" /> | Reports context.Context values stored in structs. |
| <CheckIdentity name="test-context" optIn /> | Reports detached test-owned goroutines rooted in a never-cancelled context. |
| <CheckIdentity name="nil-context" /> | Reports definitely nil context.Context arguments. |

\* Opt-in; requires explicit selection.
{/* gohawk:generated-checks:end */}

## Why this is flagged

Keeping `context.Context` as the first parameter makes cancellation and
deadlines easy to pass through a call chain. Storing a context or passing nil
can give it the wrong lifetime or cause failures far from the call site.
Detached test work rooted in a never-cancelled context can survive the test;
`t.Context()` and `b.Context()` are cancelled automatically during teardown.

Further reading: [Package context](https://pkg.go.dev/context),
[Contexts and structs](https://go.dev/blog/context-and-structs).

## How to fix it

Accept the context as the function's first parameter and pass it directly to
the work that needs it. Do not store it in a struct or pass nil; use an
appropriate real context. For a detached test-owned goroutine that observes
cancellation, use `t.Context()` or `b.Context()`, explicitly cancel and join
the worker, or give it another proven stop lifecycle. Synchronous calls using
`context.Background()` are accepted.
