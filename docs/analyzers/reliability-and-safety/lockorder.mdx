## What it detects

Acquire locks consistently and release them on every return path. A missing
unlock is reported only when another path demonstrates that the function owns
the corresponding release policy.

### Checks

| <CheckIdentity name="contradictory-order" tier="extended" /> | hazard | extended | Reports two locks acquired in opposite orders in different places. |

## Why this is flagged

Two goroutines that acquire the same locks in different orders can wait on each
other forever. Failing to unlock on one return path can similarly block every
later caller that needs the lock.

### Which locks are compared

Two mutexes held in a package variable are compared as the individual locks
they are. A mutex held in a struct field is compared by the field it is
declared in, because there is no way to tell whether the receiver in one
method is the object another method locks. Ordering is therefore reported
against the declaration: taking one field before another in one place and the
reverse elsewhere leaves the program without a consistent order, even where
today's callers happen to pass different objects.

Two locks of the same declaration are not compared. Whether
`transfer(from, to *Account)` conflicts with a caller passing the same pair in
the other order depends on the objects involved, and nothing in the code
settles that, so the pattern is accepted.

### Writes under a read lock

A read lock is shared: any number of readers may hold it at once. Writing to
the object it protects while holding only the read lock therefore races with
every other reader, and it needs nothing unusual from a second goroutine.

The report is about the object rather than about which field a lock guards.
Working out which of several mutexes covers a particular field is not something
this analyzer attempts, so a write is left alone when another lock on the same
object is held for writing, when the value being written was loaded out of the
object and is a separate cell, or when the field is updated atomically.

### Releasing with the wrong method

A `sync.RWMutex` keeps separate reader and writer state, so a lock taken with
`Lock` must be released with `Unlock`, and one taken with `RLock` with
`RUnlock`. Mixing them is not untidy but fatal: the runtime reports an unlock
of an unlocked mutex and stops the process.

The acquisition has to be visible on the same path for the mode to be known, so
a helper that releases a lock its caller took is left alone.

## How to fix it

Choose one order for acquiring multiple locks and use it everywhere. Arrange
the matching unlock as soon as each lock is acquired, commonly with `defer`, so
early returns cannot leave it held.
