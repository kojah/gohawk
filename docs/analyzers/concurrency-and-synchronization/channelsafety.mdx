## What it detects

Reports sends reachable after the same channel has been closed, and a narrow
class of channel-only deadlocks.

Complete concurrency summaries expose closes and sends inside synchronous
helpers, including imported helpers. A close in one call can therefore be
matched to a later direct send or helper call on the exact same channel.
Diagnostics point to the caller's send (or sending call), with a related
location for the close (or closing call).

This supplements the existing local flow proof; it does not require the
caller itself to be straight-line. The summary path declines branching or
opaque helper bodies and uncertain identities. Deferred and asynchronous
calls are not treated as executing at their registration or launch site.
Send-after-close comparisons do not cross loop backedges or compare events
within one call.

The experimental dependency-cycle check uses complete ordered summaries for
one caller and at most four children. It requires two distinct fresh,
unbuffered channels. If the caller and a worker each try to send first, or
each try to receive first, and each needs the other's later operation to
complete, neither first action can finish. A complete event graph proves both
blocking dependencies before reporting a cycle.

An extra sender or closer, a buffered or externally supplied channel, an
opaque participant, a branch or `select` alternative, or an unknown effect
makes that proof inconclusive. The check does not model general channel
protocols or infer a deadlock from a graph cycle alone.

The synchronization summary now records the mutually exclusive arms of a
bounded `select`, including a nonblocking default arm and a worker's bound
channel identities. This is evidence for future path-specific proofs, not a
linear operation: the dependency-cycle check still declines a graph with
unresolved alternatives. In particular, a cancellation receive cannot be
flattened into an unconditional blocked send.

## Why this is flagged

Sending on a closed channel is a run-time panic, not an error a caller can
recover from in the normal flow, so a reachable send-after-close is a latent
crash. It usually means two parts of the code disagree about which one owns
closing the channel.

Further reading: [The Go Programming Language Specification: Close](https://go.dev/ref/spec#Close).

## How to fix it

Move the close after the final send or separate the channel lifetimes.

### Accepted code

```go
func deferredCloseAfterSends(values []int) <-chan int {
  events := make(chan int)
  go func() {
    defer close(events)
    for _, value := range values {
      events <- value
    }
  }()
  return events
}
```
